## 一、为什么之前没爬到解析（根因，已实测）

| 事实 | 实测证据 |
|---|---|
| `tiku.db` 95,867 行 / 55,958 唯一题，`analysis` **100% 为空** | 数据库统计（2026-08-12） |
| 爬虫所用 `GET /api/{subject}/questions?ids=` 返回字段**无 `analysis`**（只有 id/content/material/options/correctAnswer/hasVideo 等） | 接口实测 |
| 网页版解析的真正来源是 `GET /api/{subject}/solutions?ids=`，返回 `solution`（HTML）+ `keypoints` 等 | 接口实测 |
| solutions 接口**需登录**（游客 401）；当年爬虫是游客模式（纯 GET 主链路） | 接口实测 |

结论：`normalizeQuestion` 里 `analysis: stripHtml(q.analysis)` 引用的字段在 questions 接口中不存在，所以永远存空。README 旧说法"粉笔把文字解析做成会员视频"不准确——**普通登录即可拿到文字解析**。

## 三、历史封号教训（2026-08 实测经验，本方案的设计依据）

1. **2026-08-06 被封案例**：`POST /api/xingce/exercises` 创建练习 **12~14 套/分钟** → 403「您创建练习的频率过高，请稍候再试」，连续 1,943 次失败，**26+ 分钟未解除**。关键判断：403 是**接口级限流**（GET 题目接口不受影响）。
2. **2026-08-09 账号级风控案例**：多账号并行时，账号 2 四题库全部 403（账号级封禁），换账号 3 立即正常 → **账号级风控存在，多账号可分摊 + 快速切换**。
3. **2026-08-08 稳定策略（后来一直用）**：纯 GET 链路 + 每请求 4s 间隔 + 随机抖动；403/429 冷却 90s；连续 10 次失败暂停 5 分钟；连续 50 次失败自动退出；退避 30→60→120→240 分钟。**慢速补 600+ 套未触发，高频才触发**。
4. **总结**：被封的都是高频；纯 GET 慢速从未被封。**solutions 是 GET 接口但需登录（绑定账号），按「半保守」档限速**。

## 四、执行方案

### 1. 账号准备（需用户配合）
- 用户提供最多 5 个账号的登录态：每账号一个 Chrome 窗口登录 https://www.fenbi.com → 用 `lib/extract-cookie.mjs`（或手动复制）导出为 `cookie.txt`（账号1）、`cookie2.txt`…`cookie5.txt`
- 启动前**统一探测**每个账号：GET 1 题 solutions
  - `200` = 可用 → 加入轮换池
  - `401` = 登录失效 → 剔除并提示用户
  - `403` = 已被风控 → 剔除，冷却后重测
- 探测是只读 1 次请求，无风险

### 2. 爬取节奏（默认保守档，可调）
| 参数 | 值 | 依据 |
|---|---|---|
| 批量 | 300 ids/请求（179 批） | 实测 300 全通过 |
| 每批间隔 | **2s + 随机抖动 0~1s** | 历史稳定策略 4s/请求；solutions 是 GET，取半保守 |
| 每账号连续批数 | 20 批（≈6,000 题）后**休息 3 分钟** | 防止单账号长跑 |
| 账号轮换 | 每 20 批自动切下一账号（round-robin） | 多账号分摊 |
| 并行度 | **默认 2 账号分片并行**（--shards=2）；观察 10 分钟无 403 再决定是否加到 3~5 | 5 账号是上限不是起点 |

- 单账号耗时估算：179 批 × ~2.5s ≈ 7.5 分钟纯请求 + 休息；2 账号并行 ≈ **12~18 分钟**总时长；5 账号 ≈ 6~10 分钟
- **原则：保账号优先于速度**——被封一个账号的代价远大于省几分钟

### 3. 风控响应（写进脚本，自动执行）
| 信号 | 判定 | 动作 |
|---|---|---|
| `401` | cookie 失效 | 剔除该账号，换下一个 |
| `403` body 含「频率过高」 | 接口/账号风控 | 该账号冷却（指数退避 30→60→120→240 分钟），换下一账号继续 |
| `403` 其他 / 验证码页 | 疑似封禁 | 立即全停 + 报告，不硬闯 |
| 单批连续失败 3 次 | 网络/服务端问题 | 指数退避重试（30s→1m→2m） |
| 全局连续失败 50 次 | 严重 | 自动退出，保留进度 |
| 5 账号全部被风控 | 最坏情况 | 停止，等待解封（历史：小时级封锁，慢速下基本不会发生） |

### 4. 断点续爬
- 进度文件 `solutions-progress.json`：记录已完成 questionId 集合 + 失败批队列
- 中断后重跑自动跳过已完成，只补失败批
- 每批成功即写盘（防进程被杀丢进度）

### 5. 写入
- 解析按返回 JSON 的 `id` 字段定位（不按请求顺序），防止串题
- `UPDATE questions SET analysis=stripHtml(solution), analysisHtml=solution, hasVideo=? WHERE questionId=?`（幂等）
- 申论无解析的题保留空（不报错，记录统计）

### 6. 验证（爬完后）
1. 统计：analysis 非空行数 / 覆盖率（目标：行测+职测 100%，申论 ~80%）
2. 抽查 10 题：解析内容与题干匹配（含公式图 `<img flag="tex">` 的题）
3. 跑 `npm test --prefix fenbi-crawler`（verify-db + e2e-check）
4. 汇报：耗时、各账号请求数、风控事件、未覆盖清单

## 六、风险与说明

- solutions 为 GET 接口，历史上纯 GET 链路从未被封；主要风险是**单账号长时间高频**，已用轮换+休息+冷却三重防护
- 只读不写粉笔侧任何东西（无 POST），不会产生做题记录污染账号
- 综应官方无解析，维持 App 现有 AI 解析方案不变

## 七、执行结果（2026-08-12 15:11）

### 实际执行参数
- 账号：4 个（cookie.txt ~ cookie4.txt，历史登录态），round-robin 轮换，**全程零 403/401/风控事件**
- 节奏：300 ids/批、2s±1s 间隔、每账号 20 批休息 3 分钟（方案保守档）
- 请求量：约 260 批（含探测），总耗时约 17 分钟

### 覆盖结果（唯一题）
| 科目 | 总数 | 有解析 | 覆盖率 | 说明 |
|---|---|---|---|---|
| 公务员·行测 | 45,490 | **45,490** | **100%** | 82,910 行全部写入 |

| 事业编·综应 | 2,348 | 0 | 跳过 | 官方无解析，App 走 AI 解析 |

### 过程中的关键发现（数据事实，非 bug）
1. **职测解析存在行测库**：职测题用 `sydw` 前缀请求约 88% 返回 null，改用 `xingce` 前缀可拿到共享行测题的解析（最终 25% 覆盖即来源）；独立职测题两边都没有
2. **申论解析仅限老题**：2010 年前后的小 id 题（1100~11 万）约 31% 有解析，2020 年后大 id 题（160 万+）全部无——之前"申论 4/5 有解析"是抽样偏差（恰好抽到小 id 题）
3. **批内必须同科目**：tasks 按 questionId 全局排序会混科目，前缀按首题科目判定会漏（行测批内混入申论题在 xingce 前缀下返回 null）——脚本已改为**按科目分组分批**
4. 公式题（`<img flag="tex">`）：纯文本 analysis 中公式消失（stripHtml 预期行为），**analysisHtml 保留完整公式**，App 展示应优先用 analysisHtml
